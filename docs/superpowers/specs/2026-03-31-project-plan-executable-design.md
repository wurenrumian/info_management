# Project Plan Executable Rewrite Design

**Date:** 2026-03-31

**Goal**

在保留现有 `docs/project_plan` 目录结构和阅读入口不变的前提下，将当前项目计划补成一套可直接用于启动开发的文档体系：

1. `Phase 1` 补到可直接开始编码、联调、验收的粒度。
2. `Phase 2` 和 `Phase 3` 仅补到中等粒度，保持类似 `original_request/技术方案.md` 的说明层级。

## Scope

本次只调整文档，不改业务范围，不改技术路线，不新增原始需求之外的大功能。

保留不变的内容：

1. 项目目标与强约束。
2. 现有主文档路径和阅读顺序。
3. `Phase 1 -> Phase 2 -> Phase 3` 的整体推进方式。

本次增强的内容：

1. `Phase 1` 的任务拆分、依赖关系、联调顺序、验收清单。
2. `Phase 1` 权限、导入、审计、错误处理等模糊点的明确口径。
3. `Phase 2/3` 每个模块的目标、边界、核心数据、接口组、验收口径。

## Document Strategy

采用“保留主结构，增强内容密度”的方式，不另起第二套计划。

目标文档分工如下：

1. `docs/project_plan/01-项目总方案.md`
   - 保留项目目标、约束、角色、技术架构。
   - 补充 `Phase 1` 冻结原则与 `Phase 2/3` 的边界约束说明。

2. `docs/project_plan/02-阶段开发计划.md`
   - 将 `Phase 1` 改造成执行级计划。
   - 增加模块拆分、任务包、前置依赖、开发顺序、联调用例、完成定义。
   - `Phase 2/3` 保持中等粒度，按模块给出稳定说明。

3. `docs/project_plan/03-API规范.md`
   - 保持 `Phase 1` 作为开发主契约。
   - 为 `Phase 1` 补充接口语义、权限口径、关键业务规则、错误场景。
   - 将 `Phase 2` 的文字草案补成中等粒度接口分组说明。

4. `docs/project_plan/04-数据库设计-DDL.md`
   - 补充 `Phase 1` 的表职责、字段口径、约束策略、导入相关说明。
   - 明确哪些约束现在冻结，哪些故意延后。

5. `docs/project_plan/05-协作与验收.md`
   - 增加 `Phase 1` 开发准入条件、测试基线、联调清单、验收清单。
   - 保留 `Phase 2/3` 的协作规则与里程碑。

## Phase 1 Design

`Phase 1` 的目标不是“把基础功能做一点”，而是提供所有后续模块共享的稳定底座。它必须解决以下问题：

1. 用户身份与微信绑定如何落地。
2. 用户、管理员、班级、班级成员关系如何建模。
3. RBAC 与班级/年级范围权限如何落地。
4. Excel 导入导出如何定义模板、回滚、重试、错误报告。
5. 哪些管理写操作必须产生审计日志。

为达到“可直接开工”的标准，`Phase 1` 文档需要补出：

1. 模块拆分
   - Auth / Identity
   - User & Class Admin
   - RBAC & Scope
   - Import / Export
   - Admin Audit

2. 任务顺序
   - 先完成数据模型和基础中间件
   - 再完成查询与写接口
   - 最后完成导入导出与审计闭环

3. 联调顺序
   - 登录绑定
   - 当前用户信息
   - 用户/班级/管理员管理
   - 导入导出
   - 审计查询

4. 验收口径
   - 权限正确性
   - 数据范围隔离
   - 导入作业可观测性
   - 审计完整性

## Phase 2 Design

`Phase 2` 不进入任务级拆解，只做到“可继续细化开发”的稳定说明。每条线统一补充以下内容：

1. 目标与边界
2. 核心数据
3. API 分组
4. 关键规则
5. 验收口径

分线如下：

1. A 线：知识库与检索
2. B 线：信息发布与精准推送
3. C 线：党团进度与提醒
4. D 线：审批流
5. E 线：文档库与电子证明

## Phase 3 Design

`Phase 3` 保持产品级和交付级描述，不进入页面实现细节。重点补充：

1. 学生端与管理端的范围边界。
2. 页面/能力分组。
3. 对后端模块的依赖关系。
4. 可用性与闭环验收口径。

## Non-Goals

本次不做以下工作：

1. 不补写完整前端页面原型。
2. 不为 `Phase 2/3` 产出 OpenAPI 级细节。
3. 不改原始业务取舍，例如自动抓取、成绩分析、多渠道通知等已排除能力。
4. 不直接开始代码实现。

## Risks And Decisions

当前需要明确的设计决策如下：

1. 接受 `Phase 1` 为执行级、`Phase 2/3` 为中等粒度的非对称深度。
2. 接受继续使用现有 `project_plan` 目录作为单一事实来源。
3. 接受 `Phase 1` 中部分数据库约束采用“当前冻结 + 明确延后”的表达，而不是假装全部已最终定稿。
