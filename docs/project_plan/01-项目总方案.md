# 01 项目总方案

## 1. 项目目标

建设信息学院学生事务一站式系统，覆盖：
1. 政策咨询标准化
2. 事务流程电子化
3. 通知发布精准化
4. 管理操作可审计

## 2. 业务边界（强约束）

1. 不接入校级“微人大”接口
2. 敏感数据存学校侧 Kingbase
3. 通知通道统一小程序订阅消息
4. 不做自动抓取公众号/网站
5. 不做成绩单解析/培养方案比对/选课推荐
6. 核心逻辑优先规则与结构化数据，不依赖通用大模型

## 3. 用户与权限

四级权限：
1. 学生（L1）：查询、提交申请、查看本人进度
2. 团支书/团干部（L2）：发布信息、管理本班事务
3. 班主任/教师（L3）：查看本班/本年级数据
4. 超级管理员（L4）：维护主数据与全局配置

权限模型：RBAC + 数据范围（班级/年级）

## 4. 技术架构

1. 后端：Go + Gin + GORM
2. 数据库：Kingbase（PostgreSQL 兼容）
3. 鉴权：微信登录 + JWT（Access/Refresh）
4. 文件：本地/OSS，30MB，支持分片
5. 定时任务：提醒、超时、状态扫描
6. 文档：Markdown 契约 + OpenAPI

## 5. 模块分层

1. 接口层：鉴权、参数校验、统一响应
2. 应用层：业务编排与事务
3. 领域层：状态机与规则
4. 基础设施层：DB/存储/消息

## 6. 交付原则

1. 先冻结契约（API + DDL）再并行开发
2. Phase 1 稳定后再展开 Phase 2 多线并行
3. 前端以小程序为主，管理端 Web 可选补充

## 7. 当前阶段定义

### 7.1 Phase 1 定位

Phase 1 不是“先做一点基础功能”，而是为后续所有业务模块提供稳定底座，必须一次性解决以下共性问题：

1. 微信登录、学号绑定、Token 刷新与退出登录。
2. 用户、班级、班级成员、管理员的数据关系。
3. 角色权限与班级/年级数据范围隔离。
4. 用户/班级导入导出与错误报告。
5. 管理侧关键写操作的审计留痕。

只有在 Phase 1 契约、DDL、验收口径稳定后，Phase 2 才允许并行展开。

### 7.2 Phase 2 定位

Phase 2 负责交付具体业务模块，按“知识库、发布推送、党团进度、审批流、文档与证明”五条线并行开发。Phase 2 当前只冻结模块边界、核心数据与 API 分组，不在本轮文档中展开到任务级。

### 7.3 Phase 3 定位

Phase 3 负责学生端闭环交付和管理端高频能力补齐。Phase 3 当前只冻结端侧范围、页面分组、后端依赖和验收口径，不进入页面实现细节。

## 8. 冻结与变更原则

1. `Phase 1` 的接口路径、字段语义、核心表职责、权限口径视为冻结内容。
2. 若修改 `Phase 1` 契约，必须同步更新 API 文档、OpenAPI 与 DDL 说明。
3. `Phase 2/3` 允许补充字段和页面细节，但不得破坏 `Phase 1` 已冻结的公共语义。
4. 未写入主文档的接口、表结构与流程规则，不进入联调和合并。
