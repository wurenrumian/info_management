# 02 阶段开发计划

## Phase 1：基础后端（必须先完成）

目标：建立所有后续模块的公共底座。

范围：
1. 登录与学号绑定
2. 用户、管理员、班级关系
3. RBAC + 数据范围权限
4. 导入导出（用户/班级）
5. 管理操作审计日志

交付物：
1. 可联调 API（见 `03-API规范.md` Phase 1）
2. 可导入 OpenAPI（`03-openapi-phase1.yaml`）
3. 数据库迁移脚本（见 `04-数据库设计-DDL.md`）
4. 回归测试报告

完成标准：
1. 学生端与管理端基础权限正确
2. 导入任务可回滚、可重试、可下载错误报告
3. 关键写操作有审计日志

### 1. 模块拆分

1. Auth / Identity
- 微信登录
- 学号绑定
- Access / Refresh Token
- 退出登录

2. User / Class / Admin Core
- 用户管理
- 班级管理
- 班级成员绑定
- 管理员映射与范围配置

3. RBAC / Scope
- 角色识别
- 班级范围控制
- 年级范围控制
- 超级管理员全局放行

4. Import / Export
- 用户导入
- 班级导入
- 导入作业查询
- 用户导出

5. Admin Audit
- 管理操作日志写入
- 管理日志查询

### 2. 前置依赖

1. 冻结 `03-API规范.md` 与 `03-openapi-phase1.yaml`。
2. 冻结 `04-数据库设计-DDL.md` 中的 Phase 1 表职责和字段语义。
3. 明确用户导入模板、班级导入模板、错误报告格式。
4. 明确角色与数据范围口径。

### 3. 建议开发顺序

1. 数据模型与基础配置
- 建立 `users`、`classes`、`class_members`、`admins`、`admin_logs`、`import_jobs`
- 完成枚举与索引
- 打通迁移脚本

2. 鉴权与当前用户
- `POST /auth/wechat-login`
- `POST /auth/bind-student`
- `POST /auth/refresh`
- `POST /auth/logout`
- `GET /me`
- `PATCH /me`

3. 管理基础对象
- 用户查询、详情、创建、更新
- 班级查询、创建、更新、批量绑定成员
- 管理员查询、创建、更新

4. 权限与范围控制
- 角色鉴权中间件
- 班级/年级数据过滤
- 越权返回统一错误码

5. 导入导出
- 用户导入作业
- 班级导入作业
- 作业状态查询
- 用户导出

6. 审计闭环
- 管理写操作统一记日志
- 管理日志查询

### 4. 任务包划分

1. P1-01 基础表与迁移
- 产出：Phase 1 表结构、索引、迁移脚本
- 依赖：无

2. P1-02 鉴权与会话
- 产出：登录、绑定、刷新、退出、当前用户接口
- 依赖：P1-01

3. P1-03 用户与班级管理
- 产出：用户、班级、成员绑定接口
- 依赖：P1-01、P1-02

4. P1-04 管理员与数据范围
- 产出：管理员接口、角色与范围控制
- 依赖：P1-02、P1-03

5. P1-05 导入导出
- 产出：导入作业、导出能力、错误报告
- 依赖：P1-03、P1-04

6. P1-06 审计与回归
- 产出：审计日志、回归测试报告、固定联调用例
- 依赖：P1-03、P1-04、P1-05

### 5. 联调用例

1. 学生首次登录闭环
- 微信登录成功
- 未绑定状态下提交学号与姓名绑定
- 再次获取当前用户信息

2. 管理员基础维护闭环
- 创建班级
- 创建用户
- 批量绑定班级成员
- 创建管理员范围映射

3. 导入回归闭环
- 上传用户导入文件
- 查询作业状态
- 下载错误报告
- 修正后重新导入

4. 审计闭环
- 管理端完成创建或更新
- 查询日志中可看到操作者、目标对象、动作和时间

### 6. Phase 1 完成定义

1. 所有 Phase 1 接口按 OpenAPI 可联调。
2. 权限错误、越权访问、资源不存在、业务冲突均返回统一错误码。
3. 学生、班级、管理员查询默认受数据范围控制。
4. 导入作业具备总数、成功数、失败数、错误报告路径和作业状态。
5. 所有管理侧写接口产生审计日志。
6. 提供最少一轮完整回归测试报告。

## Phase 2：后端并行模块开发

目标：在 Phase 1 契约不破坏的前提下，多人并行交付。

并行分线：
1. A线：知识库与检索
2. B线：信息发布与精准推送
3. C线：党团进度与提醒
4. D线：审批流
5. E线：文档库与电子证明

并行规则：
1. 公共字段语义不改
2. 先更新 `03-API规范.md` 的 Phase 2 部分，再开发
3. 每线独立 migration，不覆盖他线对象
4. 每线至少提供 2 条固定联调用例

### A线：知识库与检索

目标：
1. 为学生提供标准问答、办理指引、官方链接和模板下载入口。

边界：
1. 只做结构化知识条目检索与维护。
2. 不依赖通用大模型生成答案。

核心数据：
1. 知识条目
2. 关键词
3. 附件与链接
4. 生效状态与更新时间

API 组：
1. 学生端搜索与详情
2. 管理端新增、更新、上下线、分类维护

验收口径：
1. 学生可通过关键词查到标准答案或官方链接。
2. 管理员可维护知识条目并控制是否对外可见。

### B线：信息发布与精准推送

目标：
1. 支持管理员录入通知，并按范围推送给目标学生群体。

边界：
1. 只支持管理员录入，不做自动抓取。
2. 推送通道统一为小程序订阅消息。

核心数据：
1. 通知主体
2. 标签与目标范围
3. 发送记录
4. 阅读状态

API 组：
1. 通知创建、发布、撤回
2. 目标范围预览
3. 学生端通知列表与详情
4. 发送记录查询

验收口径：
1. 管理员可按年级、专业、班级等条件圈定对象。
2. 学生只能看到命中自己范围的通知。

### C线：党团进度与提醒

目标：
1. 展示党团阶段进度，并在关键节点触发提醒。

边界：
1. 先支持线性阶段管理。
2. 规则由管理员维护，不引入复杂流程引擎。

核心数据：
1. 党团类型
2. 当前阶段
3. 阶段更新时间
4. 节点提醒规则

API 组：
1. 学生端进度查询
2. 管理端阶段更新
3. 提醒规则查询与维护

验收口径：
1. 学生可查看当前阶段和关键时间点。
2. 管理员可批量更新阶段并触发后续提醒。

### D线：审批流

目标：
1. 支持学生提交简单申请，管理员在线审批并返回结果。

边界：
1. 先支持线性审批与固定状态流转。
2. 不实现通用工作流设计器。

核心数据：
1. 申请单
2. 当前审批人
3. 状态
4. 审批历史

API 组：
1. 学生提交、撤回、查询
2. 管理员待办、审批、驳回、转交
3. 流程记录查询

验收口径：
1. 学生可完整查看申请状态流转。
2. 管理员可处理待办并留存审批轨迹。

### E线：文档库与电子证明

目标：
1. 提供标准文档管理和电子证明生成能力。

边界：
1. 文档库负责模板与附件管理。
2. 证明生成优先采用结构化模板填充。

核心数据：
1. 文档与模板
2. 证明类型
3. 文件路径
4. 生成记录

API 组：
1. 文档上传、分类、查询
2. 模板维护
3. 证明申请、预览、下载

验收口径：
1. 学生可按授权范围下载标准材料。
2. 指定证明类型可基于学生信息生成 PDF 或预览文件。

## Phase 3：前端交付（小程序优先）

目标：完成学生端可用闭环，管理端可选补充。

学生端 P0：
1. 登录绑定
2. 通知与消息
3. 知识库查询
4. 进度查询
5. 审批申请与状态

管理端 P0（建议）：
1. 用户班级管理
2. 发布与推送
3. 审批处理
4. 知识库维护

完成标准：
1. 学生端 3 分钟内完成一次事务提交
2. 管理端可完成“导入 -> 发布 -> 审批”闭环

### 学生端范围

1. 登录与学号绑定
2. 首页消息与待办
3. 知识库检索
4. 党团进度查询
5. 审批申请与状态跟踪
6. 证明与文档下载

### 管理端范围

1. 用户、班级、管理员维护
2. 通知发布与目标人群选择
3. 党团进度批量维护
4. 审批处理
5. 知识库与模板维护
6. 导入导出与日志查询

### 后端依赖关系

1. 登录、权限、当前用户依赖 Phase 1。
2. 知识库、通知、党团、审批、证明分别依赖对应的 Phase 2 业务线。
3. 管理端所有写操作继续复用 Phase 1 审计能力。

### Phase 3 验收口径

1. 学生首次进入可完成登录绑定。
2. 学生可完成至少一条“查询类任务”和一条“申请类任务”。
3. 管理员可完成至少一条“导入类任务”、一条“发布类任务”和一条“审批类任务”。
4. 端侧展示结果与后端权限范围一致。
